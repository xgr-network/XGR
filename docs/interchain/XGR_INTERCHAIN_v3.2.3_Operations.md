# XGR Interchain — current runtime and independent transfer operations

**Reviewed:** 2026-10-23  
**Node baseline:** [xgr-node v3.2.3](https://github.com/xgr-network/xgr-node/releases/tag/v3.2.3)  
**Canonical implementation:** [xgr-network/xgr-interchain](https://github.com/xgr-network/xgr-interchain)  
**Status:** Mainnet implementation and operational guide; independently check live deployments. XITA's public launch is separately gated.

## Architecture and trust boundaries

XGRChain (chain/domain **1643**) is the mandatory hub. A transfer from Arbitrum (42161) to Base (8453) consists of **two independent, user-authorized hops**, Arbitrum → XGRChain → Base. Every directed route has its own route ID and source ILN Gateway. Route registration is permissionless; the validator quorum verifies independently observed source evidence and is not a route-admission committee. Validator membership and quorum security, token escrows, fee allocation and source/destination Mailbox contracts remain independent of the XITA website. No centralized relay operator can mint/unlock from an unverified message.

Each source asset has a router on its physical chain: original ERC-20 collateral is locked by a collateral router; wrapped/synthetic ERC-20 is minted only after authenticated delivery and burned before onward dispatch. Native XGR uses its native router. Current assets/routes and their distinct source/destination contracts are documented in `config/assets/`, `deployments/assets/` and `deployments/chains/` of the implementation repository. A configured prospect route is NOT proof of a live deployment.

## Direct, permissionless transfer — no commercial Fee Execution Gateway and no XITA relayer

**Important distinction:** The public protocol `ILNGateway` and the optional commercial `XITAExecutionGateway` are **different contracts**. A direct transfer **does require** the former but **does not require** the latter, an XITA commercial quote, any XITA-managed relayer, sponsor worker or operator wallet. **The user must sign and fund all source and destination transactions.** Validator services must still be available to create valid BLS/Merkle attestations, but a particular relay operator is not trusted or required.

1. Independently confirm **both directional route records**, on-chain `getRoute(destinationDomain, routeId)`, the source `ILNGateway`, source router and token, source `Mailbox` and Merkle hook, target `Mailbox`, destination ISM, deployed runtime bytecode and verified deployment receipt. Validate destination `verifyInboundRoute` and that source/destination chain IDs match your RPCs. Never derive a route from a token ticker alone. The current official manifest is [xgr-interchain deployments](https://github.com/xgr-network/xgr-interchain/tree/main/deployments); reverify live state before signing.
2. Prepare the user-controlled wallet on the **source chain**, ensure adequate native currency for gas and the required validator/router native fee, and maintain source-token balance. For ERC-20, confirm `ILNGateway.warpToken()`, then grant only the required allowance to the **ILNGateway** (not the optional commercial fee adapter). For native XGR, no ERC-20 approval.
3. Call source `ILNGateway.quoteILN(destinationDomain, bytes32(recipient), amount)` using the exact amount in base units. It returns `(validatorFeeWei, routerNativeValueWei, totalNativeValueWei, totalTokenAmount)`. For ERC-20, token principal is taken via allowance; for native XGR, ensure the quoted native value includes the native principal. Abort if returned bindings, values or allowance target differ from independently verified chain state.
4. With **your own wallet**, call source `ILNGateway.bridge(destinationDomain, bytes32(recipient), amount)` with `msg.value = totalNativeValueWei` and normal source-chain gas. Do not send a second source transfer if delivery is delayed. Record the resulting source transaction and the authenticated Mailbox message ID; verify `ILNOperation` and `Dispatch` in the finalized source receipt.
5. **Without the XITA relayer**, obtain the unsigned delivery call from the public verifier script `runtime/native-relayer/recover-iln.mjs` in [xgr-interchain](https://github.com/xgr-network/xgr-interchain/blob/main/runtime/native-relayer/recover-iln.mjs). It requires public chain RPC/contract bindings via environment variables `ORIGIN_CHAIN_ID`, `ORIGIN_DOMAIN`, `ORIGIN_ILN_REGISTRY`, `ORIGIN_ILN_GATEWAY`, `ORIGIN_WARP_ROUTER`, `ORIGIN_MAILBOX`, `ORIGIN_MERKLE_TREE_HOOK`, `ROUTE_ID`, `DESTINATION_CHAIN_ID`, `DESTINATION_DOMAIN`, `DESTINATION_WARP_ROUTER`, `DESTINATION_MAILBOX`, `DESTINATION_ILN_ISM`, `ATTESTATION_ROUTE`, `ORIGIN_RPC_URL`, `DESTINATION_RPC_URL`, `ATTESTATION_RPC_URL` and optionally `SOURCE_TX_HASH`. Run `node runtime/native-relayer/recover-iln.mjs <MESSAGE_ID>` from the implementation checkout. The script **does not broadcast**: it cross-checks the canonical source receipt, route, quorum, Merkle inclusion, fee allocation, current destination validator set and `Mailbox.process.staticCall`. `PENDING` means rerun for the **same message** after the quorum finishes. `FRESH_QUORUM_REQUIRED` means reattestation of that original message, not a new token transfer.
6. Only on a validated `READY_UNSIGNED_CALL` response, recheck `Mailbox.delivered(messageId) == false` and the destination set ID. **Sign and send the emitted `{to, data, value}` with your own wallet on the destination chain**, paying destination native gas. It calls public `Mailbox.process(metadata,message)`. Confirm `delivered(messageId) == true`, the receipt and recipient's minted/unlocked token balance. Any account is allowed to pay and submit the same authenticated delivery; the validator signature, not the transaction sender, authorizes it.

**Direct two-hop execution:** Complete the first delivery to XGRChain and confirm the user's hub asset balance. Independently reverify the XGRChain → target route, quote and pay the second source-hop fee, approve the second-hop `ILNGateway` for the hub synthetic ERC-20 (if applicable), sign `bridge` from the same wallet, then repeat the unsigned proof and destination `Mailbox.process` procedure. Do not assume the commercial `continueJourney` linkage, quote/sponsorship or single-operation XITA UI recovery exists in the direct path: keep **both** source transaction hashes and message IDs. Ensure no duplicate source `bridge` transaction is signed while recovering a previous hop.

The checker is public-source software; ordinary operators must install dependencies, use known-good RPCs, independently verify commands and calldata and obtain any missing gas themselves. Source-chain archival access may be needed for earlier receipts/logs. Using this protocol does not imply that XITA promises to provide RPC, relayer, free gas or emergency recovery.

## Operators, validators and resilience

Validator nodes attest authenticated messages and exchange independently verified Merkle replicas via P2P; **validation is separated from delivery/gas execution**. A validator can also submit destination transactions as an ordinary gas-paying executor, but that would add cross-chain funding, nonce, key-management, reliability and liability obligations. No special validator status is needed to deliver an already authorized message. Reusable delivery calldata means multiple independent relayers, users or third parties can execute it. The destination Mailbox's message-ID replay protection must be checked.

For runtime diagnostics, query `xgr_getILNIndexerStatus`, `xgr_getILNQuorum`, `xgr_getILNQuorumAttestation`, and `xgr_getILNReplicaProof` where supported. In v3.2.3 the Merkle-replica P2P cold sync can recover a missing prefix from a peer with a verified complete replica. The local recent-hook catch-up window is bounded; if **every** peer lacks the complete prefix, an operator may need a verified one-off `./manage.sh init-merkle --dry-run` and controlled bootstrap using canonical Hook logs. Never substitute fabricated roots, disable quorum verification or repeat source locks while recovering.

## Commercial XITA interface is optional

The XITA website's fee Execution Gateway adds a separately disclosed **commercial service fee** and EIP-712 quote and provides journey progress. Its optional gas sponsor may transfer native coins **to** a user's wallet for eligible steps. Neither feature is needed to call the public protocol ILN Gateway. XGR.Network GmbH does not receive a user's wallet private keys and does not sign user transfers. Locked ERC-20 collateral is held **by public smart-contract escrows**, not in the company's discretionary custodial wallet. Availability and settlement are dependent on independent chains, RPC access, on-chain contracts and validator attestations.

## Version/status discipline

Documents dated October 4, 2026 describing `xgr-node v3.1.1`, `v3.1.3` planned routes, `bridge.xgr.network` and `xgr-hyperlane` must be treated as legacy deployment descriptions. Their historical addresses and activation assumptions are **not** current route authority. Always use verified current deployments, EVM state and the latest running node binary.
